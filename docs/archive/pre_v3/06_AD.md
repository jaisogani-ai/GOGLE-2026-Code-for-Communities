# 06 — AD: Architecture & Deployment

**"AD" in this repository means Architecture & Deployment.** It is expanded here
because the acronym is otherwise ambiguous (Architecture Decision, Active
Directory, Architecture Diagram) and a document whose title has to be guessed at
is a document that gets misread.

This document describes the target Google-native topology, the environments,
CI/CD, monitoring, the release process, acceptance criteria, and two checklists:
operational readiness and demo readiness.

---

## 0. The statement that governs the whole document

**None of this is currently deployed.** There is no Google Cloud project, no
Cloud Run service, no Firestore database, no BigQuery dataset, no Gemini API key
in use anywhere in this repository, and no user. What runs today is a Python
package, a FastAPI process started by `make api`, a static HTML workspace built
by `build_web.py`, and 62 tests. The event store is in-process and does not
survive process exit.

Everything in §1–§6 is therefore a **target architecture**: a design that the
current code is structured to accept, not an environment that exists. Where this
document says "Cloud Run does X", read "Cloud Run would do X". The checklists in
§8 and §9 are the honest measure of distance between the two.

---

## 1. Why this shape

The architecture is driven by three properties of the problem, not by a
preference for any vendor:

1. **Capture happens where connectivity does not.** A store clerk counting
   physical stock in a PHC cannot depend on a network round-trip. Evidence
   capture must be local-first and must survive hours offline without the
   operator thinking about it.
2. **The audit chain must be append-only and replayable.** No computed status is
   stored; state is a replay of events. That forbids a mutable-row design as the
   system of record.
3. **Tathyon is a sidecar, not a system of record.** e-Aushadhi / DVDMS remains
   the book of record. Tathyon holds claims about it, evidence against it, and
   the verified state a third party may rely on. This keeps the integration
   surface narrow and the deployment small.

```
   FACILITY (offline-tolerant)            GOOGLE CLOUD (stateless where possible)
   ┌──────────────────────────┐          ┌────────────────────────────────────┐
   │ capture client           │          │ Cloud Run: ingest-api              │
   │  photo + nonce + count   │──sync──▶ │   claim → detect → event append    │
   │  Firestore local cache   │          ├────────────────────────────────────┤
   └──────────────────────────┘          │ Cloud Run: verify-api              │
                                         │   posterior, state machine         │
   ┌──────────────────────────┐          ├────────────────────────────────────┤
   │ district workspace (web) │◀────────▶│ Cloud Run: decision-api            │
   │  decision + reasons      │          │   OR-Tools CP-SAT in-process       │
   │  + audit timeline        │          ├────────────────────────────────────┤
   └──────────────────────────┘          │ Firestore  event store + capture   │
                                         │ BigQuery   analytical panel        │
   ┌──────────────────────────┐          │ Gemini     transcription only      │
   │ e-Aushadhi / DVDMS       │──feed──▶ │ Cloud Storage  evidence artifacts  │
   │ (system of record)       │          └────────────────────────────────────┘
   └──────────────────────────┘
```

## 2. Cloud components

Each component is stated with purpose, failure mode, cost consideration, and
replacement strategy. The replacement column is not decoration: a verification
layer that can only exist on one vendor's infrastructure is not credible to a
government buyer, and the exit cost should be known before the entry cost.

### 2.1 Cloud Run — stateless services

**Purpose.** Hosts three stateless services: `ingest-api` (claim intake,
detection, event append), `verify-api` (posterior, state machine, attestation
write), and `decision-api` (risk, forecast, gated optimisation, counterfactual).
Stateless because state lives in the event log; any instance can serve any
request by replaying.

**Failure mode.** Cold starts on a request that carries a CP-SAT solve, turning
a 5-second solve budget into a 12-second user-visible wait. A concurrency
setting too high starves the solver of CPU and causes `time_limit_s` to expire
with a feasible-but-poor solution — which is silent, and therefore the dangerous
version. Mitigation: minimum instances ≥ 1 on `decision-api`, concurrency 1 on
that service only, and the solver status (`OPTIMAL` / `FEASIBLE` / `UNKNOWN`)
surfaced in the decision object rather than discarded.

**Cost consideration.** Request-billed, so district-scale traffic is negligible;
the cost driver is the minimum-instance floor on `decision-api` and the CPU it
holds. Keeping the solver on its own service means the floor is paid for one
service, not three.

**Replacement strategy.** The services are plain FastAPI ASGI apps with no
Cloud Run SDK in the code path. They run under any container runtime — GKE,
Cloud Functions gen2, an on-premise Kubernetes cluster inside a state data
centre, or `uvicorn` on a single VM. This matters specifically because health
data localisation may require an on-premise deployment; the code should not have
to change for that.

### 2.2 Firestore — offline-first capture at facilities, and the event store

**Purpose.** Two distinct jobs. (a) At the facility: the capture client writes
evidence and draft attestations to Firestore's local cache; the SDK syncs when
connectivity returns. This is the only reason Firestore is in the design — the
offline persistence and conflict handling are the product, not the database.
(b) In the cloud: the append-only hash-chained event collection, one document
per event, with the chain hash as a field.

**Failure mode.** Firestore has no server-enforced append-only semantics, so the
immutability of the chain rests on security rules plus the hash chain itself. A
rule misconfiguration permitting update or delete would not corrupt detection —
`verify_chain()` still returns the offset at which the chain broke — but it
would permit a silent deletion at the tail. Mitigation: security rules allowing
create only; a periodic chain-length and head-hash assertion; and the head hash
mirrored to a second store so a truncation is detectable, not merely a shorter
chain. Second failure mode: a long-offline device syncing a large backlog can
produce a write burst that hits per-document and per-collection write limits.

**Cost consideration.** Billed per read/write/delete and per GB stored. The
event model is write-heavy and read-light per event, which suits it; the risk is
a workspace UI that re-reads a full audit timeline on every render. Timelines
must be paginated by offset and cached, or the read cost scales with attention
rather than with activity.

**Replacement strategy.** Postgres with an append-only table, a `BEFORE UPDATE
OR DELETE` trigger that raises, and a generated chain-hash column gives stronger
immutability guarantees than Firestore does. The offline half is the hard part
to replace: a PouchDB/CouchDB pair or a locally-queued SQLite with an explicit
sync protocol are the realistic substitutes, and both mean writing sync code
that Firestore gives for free. Exit cost is concentrated here.

### 2.3 BigQuery — the analytical panel

**Purpose.** The panel used for evaluation, the yield curve, the counterfactual
at district scale and the forecasting backtests. Not in the decision path — the
gate never queries BigQuery. This separation is deliberate: an analytical store
that can go stale must never be able to make a claim look verified.

**Failure mode.** Staleness presented as currency. If the workspace renders a
BigQuery-derived figure beside a Firestore-derived verified state, an operator
will read both as equally current. Mitigation: every BigQuery-derived number in
any UI carries its own `as_of`, and no such number may appear inside an
attestation or a certificate.

**Cost consideration.** On-demand query pricing punishes `SELECT *` over the
ledger panel; partition by date and cluster by facility and SKU. At the scale
described in `14_LIMITATIONS.md` (48,000 rows) this is free; at national scale
the backtests, not the dashboards, are the cost.

**Replacement strategy.** The panel is a set of parquet files today
(`data/*.parquet`) read by pandas. DuckDB over object storage reproduces the
analytical behaviour at district scale with no vendor dependency; Postgres with
partitioning works at state scale. Low exit cost — this is the least locked-in
component.

### 2.4 Gemini — transcription only

**Purpose.** Transcribes what a human has already written on a physical count
sheet, and reads a serial plate on an asset. It does not count, does not judge,
and does not narrate over unverified state.

**Failure mode.** The catastrophic failure is not a wrong transcription — it is a
wrong transcription that gets **signed**. Vision-language models score 0.23–0.58
on object counting, which is why the human counts. The control is that
low-confidence cells render blank-to-fill and are never pre-filled; pre-filling
would launder a model error into a signed record. The ordinary failure modes —
latency, rate limits, region availability — degrade to manual entry, which is
the pre-existing process and therefore an acceptable floor.

**Cost consideration.** Per-token/per-image billing on a workload proportional to
verification volume, which is exactly the volume the business model is priced
against (see `archive/15_STARTUP_STRATEGY.md`). This cost must be tracked per
verification, not per month, or the unit economics become invisible.

**Replacement strategy.** The seam already exists: today's code path is a mock
adapter (`gemini-transcription-adapter/mock`) behind a fixed interface that
emits a typed evidence event with an `extraction_model` field and a confidence
per cell. Any OCR or VLM — Cloud Vision, a self-hosted TrOCR, Tesseract for
printed plates — substitutes at that seam. **Honest status: no Gemini API call
is made anywhere in this repository.** The boundary is designed; the integration
is not built.

### 2.5 OR-Tools CP-SAT — in-process

**Purpose.** The constrained redistribution solve. Runs in-process inside
`decision-api`; no solver service, no queue, no distributed optimisation.

**Failure mode.** The solve returning `FEASIBLE` rather than `OPTIMAL` inside the
time limit and that distinction being dropped on the way to the UI. Also the
class of failure already found once in this codebase: `IntAffine` has no
`__floordiv__` in current OR-Tools, so the objective raised `TypeError` and
**every solve was dead** until the coefficient was reduced to a Python int
before multiplying the variable. An in-process solver with a version-sensitive
API needs a pinned version and a test that asserts a non-trivial solve, not just
that the call returns.

**Cost consideration.** CPU inside an existing Cloud Run instance; no separate
line item. The cost is latency budget, not money.

**Replacement strategy.** The model is expressed against the CP-SAT Python API.
Moving to a MIP formulation under HiGHS or CBC is a rewrite of
`optimize.optimise` but not of anything around it, because the interface is
`(facilities, sources, needs) → Decision` and the gate lives outside the solver
— unverified stock never reaches it. That is the important architectural
property: **the gate is not a solver constraint.** Replacing the solver cannot
weaken the gate.

### 2.6 Cloud Storage — evidence artifacts

**Purpose.** Photographs and capture artifacts. The event log stores the
artifact hash and a perceptual hash; the bytes live here.

**Failure mode.** An artifact deleted or lifecycle-expired while its hash is
still referenced by a signed attestation, leaving an attestation that cannot be
re-verified against its evidence.

**Cost consideration.** Storage grows monotonically with verification volume and
never shrinks, because evidence supporting a signed attestation cannot be
deleted. Retention policy is a legal question before it is a cost question.

**Replacement strategy.** Any S3-compatible object store, including MinIO
on-premise. Trivial substitution; the code holds hashes, not URLs to a specific
vendor.

## 4. CI/CD

**Target pipeline, per commit:**

1. `pip install -r requirements.txt` in a clean container, from the lock file.
2. `make data` — regenerate the synthetic corpus from the seed. If the seed
   produces different data than the committed artifacts imply, that is a
   failure, not a warning.
3. `make eval` — must complete and write `artifacts/eval_report.json`.
4. `make demo` — must complete and write `artifacts/demo_scenario.json`.
5. `make test` — **62 tests must pass.** Zero tolerance; no skips permitted in CI
   without an explicit, reviewed xfail reason.
6. Artifact diff gate: if `eval_report.json` metrics move beyond a declared
   tolerance, the build does not fail, but the diff is posted to the PR and must
   be acknowledged. Metrics changing silently is how honest numbers rot.
7. Container build, pinned base image, vulnerability scan.
8. Deploy to `staging` on merge to main; `prod` deploy is manual and gated.

**Current status: none of this exists.** There is no CI configuration in the
repository. `make all` is run by hand on a developer machine. This is the single
largest gap between "it works" and "it keeps working", and it is listed as
blocking in §9.

## 5. Monitoring

What would be monitored, grouped by what the alert would actually mean:

**Integrity (page immediately).**
- `verify_chain()` returns a non-null break offset. This is not a performance
  alert; it means the audit chain is compromised.
- Event-log head hash diverges from its mirror.
- An attestation written where attester = custodian. The store raises on this
  path, so an occurrence means the enforcement was bypassed.

**Gate behaviour (the product's vital signs).**
- Rate of `BLOCKED_VERIFICATION_REQUIRED` per district per week. A rate falling
  toward zero means either the data got better or the gate got disabled, and
  those must be distinguished.
- Break-glass override count, by actor and by role, with the age of every
  outstanding verification obligation. **An override with an expired obligation
  is the metric that decides whether this system is real.**
- Blocked sources that are never subsequently verified — the queue that quietly
  grows is how a gate becomes theatre.

**Model (degrade, do not page).**
- Trust-model PR-AUC on newly labelled records against the deployed baseline
  (today: **0.079** against a base rate of **0.053**, with the deterministic
  staleness rule at **0.047**).
- Forecast MASE by ADI stratum, because the pooled number is known to be
  misleading on this corpus (**TSB 0.709 vs naive 0.699** pooled; TSB **0.819**
  vs naive **0.827** on **ADI > 1.32**).
- Share of Gemini cells returned below the confidence threshold, i.e. how much
  of the transcription burden is falling back to the human.

**Operational.**
- Cloud Run cold-start rate and solve latency on `decision-api`, with solver
  status distribution.
- Capture-client sync backlog age at the 95th percentile — the honest measure of
  whether offline-first is working.

**Current status: none of this is instrumented.** There are no metrics, no
traces, no dashboards, no alerts.

## 6. Release process

1. Every change lands via PR. A change touching `optimize.optimise`,
   `store.put_attestation`, `verify` state transitions or `detect.FEATURES`
   requires a second reviewer, because those four are where the guarantees live.
2. The 62-test suite passes, with `test_gate.py` and `test_no_leakage.py`
   explicitly named in the merge record.
3. `make all` is re-run and both artifacts regenerate.
4. Version tag; the model card and the limitations document are reviewed for
   staleness in the same commit. A metric that changed and a document that did
   not is a release blocker. (`14_LIMITATIONS.md` is currently stale in exactly
   this way — it states there are no tests, which was true when written and is
   now false. That is the defect this step exists to catch.)
5. Deploy to `staging`, run the demo script end-to-end against it.
6. Manual promotion.

## 7. Acceptance criteria

A build is acceptable when all of the following hold. These are binary, and each
is checkable by running something.

| # | Criterion | How it is checked |
|---|---|---|
| AC1 | `make all` completes from a clean clone with no manual step | Run it in a fresh container |
| AC2 | 62 tests pass, 0 failures, 0 unexplained skips | `make test` |
| AC3 | The hash chain verifies; the tamper test returns the breaking offset | `test_gate.py`, chain replay |
| AC4 | Unverified stock cannot be transferred under any input | `test_gate.py` |
| AC5 | A blocked decision returns HTTP 200 with a typed decision, not an error | `test_api.py` |
| AC6 | An attestation by the custodian is rejected at write time | `store.put_attestation` raises |
| AC7 | No ground-truth column and no violation flag appears in `detect.FEATURES` | `test_no_leakage.py` |
| AC8 | `artifacts/eval_report.json` and `artifacts/demo_scenario.json` are regenerated, not edited | Regenerate and diff |
| AC9 | Every number shown on stage traces to one of those two artifacts or is labelled a hypothesis | Manual review against `13_DEMO_SCRIPT.md` |
| AC10 | The GFR-22 certificate refuses to emit when evidence does not support the claimed status | `make demo`, scene 2 |

## 8. Operational readiness checklist

Honest status against the target deployment. Nothing here is checked.

- [ ] Google Cloud project, billing account, IAM roles defined
- [ ] Firestore security rules permitting create only; update and delete denied
- [ ] Event-log head hash mirrored to an independent store
- [ ] Durable event store (today the chain is rebuilt in-process every run and does not survive exit)
- [ ] Authentication and authorisation (today there is none; roles are carried on events but not enforced by any middleware)
- [ ] Real signing keys (today the attestation signature is the literal string `sig:prototype-software-keypair`)
- [ ] Break-glass obligation durably recorded, with deadline expiry and escalation
- [ ] Backup and point-in-time restore, with a restore actually rehearsed
- [ ] Evidence retention policy agreed against the policy-based requirement
- [ ] Data-residency position for health data established
- [ ] Rate limiting and abuse controls on capture endpoints
- [ ] Incident runbook, specifically for a chain-break alert
- [ ] On-call rotation
- [ ] Load test at district scale, then at state scale
- [ ] Penetration test
- [ ] DPIA / privacy review (Tathyon holds no patient PII, which narrows but does not remove this)
- [ ] Integration contract with e-Aushadhi / DVDMS agreed with whoever owns it

**Count: 0 of 17 complete.** The system is a working prototype, not an
operational service, and the distance is this list.

## 9. Demo readiness checklist

These are the items that decide whether the demo survives contact with a room.

- [ ] **The demo must run from a clean clone via `make all`.** Clone into an
      empty directory, fresh virtualenv, `pip install -r requirements.txt`,
      `make all`. Any manual step, any pre-existing artifact, any locally-cached
      state disqualifies it. *Not yet verified — it has only ever been run in a
      working tree.*
- [ ] Rehearsed at least twice end-to-end, timed, on the presenting machine
- [ ] `make all` timed; if it exceeds the slot, the demo runs against
      pre-generated artifacts **and the presenter says so out loud**
- [ ] Pre-recorded fallback capture exists and replays **through the unmodified
      server path** (§ `13_DEMO_SCRIPT.md` fallback plan). *Not recorded.*
- [ ] Wifi-off moment rehearsed on the actual venue network, including the
      failure where the machine silently rejoins
- [ ] Every figure on every slide traced to `artifacts/eval_report.json` or
      `artifacts/demo_scenario.json`, or explicitly labelled a hypothesis
- [ ] The honest-metrics slide is in the deck and is **not** the last slide
      skipped for time — it includes the D1 detector failure and the pooled-MASE
      loss
- [ ] The synthetic-data disclaimer is stated in the first 30 seconds, not in a
      footnote
- [ ] The Gemini adapter is described as a mock interface if asked, without
      hesitation
- [ ] Laptop power, adapter, offline copy of the repository on a USB stick
- [ ] Browser zoom set so the reason codes are readable from the back of the room

**Two of these are currently blocking: the clean-clone verification and the
fallback recording.** Both are on the critical path in `archive/05_WBS.md` (K4, K6).
