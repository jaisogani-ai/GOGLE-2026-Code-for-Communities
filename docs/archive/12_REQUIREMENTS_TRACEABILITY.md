# 12 — Requirements Traceability

Mapping from the "Build with AI: Code for Communities 2.0, Track 3 — Smart Health
& Supply Chain Resilience" challenge requirements to what actually exists in this
repository.

## Status vocabulary

| Status | Meaning |
|---|---|
| `IMPLEMENTED` | Code exists, runs, and does the thing end to end on synthetic data |
| `PARTIAL` | Core mechanism exists; named components are missing |
| `ARCHITECTURAL_ONLY` | Designed, with data model support, but no working implementation |
| `NOT_IMPLEMENTED` | In scope, not built |
| `DELIBERATELY_EXCLUDED` | In the challenge brief, and we chose not to build it. Reason given. |

**A note on the Test column that applies throughout.** The `tests/` directory in
this repository is **empty**, and `tathyon/eval.py` — referenced by three module
docstrings — **does not exist**. Every entry below marked "specified, absent"
means exactly that: the module docstring names a test, and the file is not there.
Nothing in this repository is covered by an executing automated test.

## The two exclusions, argued

### Personnel attendance — `DELIBERATELY_EXCLUDED`

The Track 3 brief lists personnel attendance alongside stock and beds. We are not
building it, and the reason is not effort.

**It is personal data.** Attendance is information about identified individuals,
processed under India's Digital Personal Data Protection Act 2023. Building
attendance into Tathyon would pull the system into a materially heavier
obligations regime — purpose limitation, notice and consent, data-principal rights
including correction and erasure, breach reporting — for a feature that is
adjacent to, not part of, the core loop. Every other object in the system is about
a *thing*: a batch, a shelf, a ventilator. The moment the system is about a
*person*, its risk profile changes completely, and so does what a breach means.

**And the buyer would be the person surveilled.** The customer for Tathyon is a
state health department. The people whose attendance would be tracked are that
department's own staff — including the facility in-charges and block supervisors
who are also the *attesters* the entire verification model depends on. A tool that
both asks a nurse to make an honest physical attestation and reports her arrival
time to her employer has a conflict at its centre. The honest attestation is the
product; the surveillance would undermine the willingness to give it.

There is also a design objection. Attendance state flips several times a day and
is not physically verifiable by photograph in any meaningful sense — the evidence
model here (nonce in frame, perceptual dedupe, human counts and AI transcribes)
is built for slow-moving physical quantities and does not transfer.

This is a scope decision we would defend to a judge, not a gap we would close
with more time.

### Bed availability — `ARCHITECTURAL_ONLY`

Beds are in scope conceptually and are genuinely not built, for a reason that is
about the physics of the quantity rather than about effort.

**Bed state flips in one step.** A bed goes from occupied to free at a discharge
and back at an admission — a discrete event, possibly minutes apart. Tathyon's
freshness model is a Gamma-Poisson posterior over *gradual drawdown*: it answers
"a human counted 400 boxes eleven days ago, how many are there now" by integrating
a consumption rate over a gap. That model is meaningless for a quantity that
changes by ±1 instantaneously and unpredictably. A posterior over bed occupancy
eleven days after a physical count would be uninformative, and dressing it up as a
number would be worse than saying nothing.

**So beds must be event-fed, not photo-verified.** The correct architecture is to
ingest admission and discharge events from the hospital information system as
first-class `StateEvent`s — the event store already supports this, and
`EventType` already contains `CONSUMED` and `RECEIVED` analogues — and to use
periodic physical verification only as a *reconciliation* check against drift,
not as the primary source. That is a different ingest integration from the one we
built, against a system we do not have access to.

What *would* carry over unchanged: the claim/attestation separation, the
custodian/attester rule, the event log, the gate pattern (do not allocate a bed
you cannot evidence), and the reason-code vocabulary. What does not carry over: the
photo-evidence pipeline and the quantity posterior.

We would rather say "we did not build beds, and here is the architecture that
would" than ship a bed count whose freshness model we know to be wrong.
